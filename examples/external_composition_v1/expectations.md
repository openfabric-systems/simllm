# External serving composition expectations

This prospective COMP-88 study promotes the eight already published external
adjustments into one immutable composition record. It checks a new installed
binding and new declared interventions. The earlier service values and
comparison records are known regression oracles, not newly predicted or
newly measured outcomes. The exact input identities and grids are frozen in
[expectations.json](expectations.json).

The source is the pinned Qwen3-32B-FP8 TensorRT-LLM composition on H200. Its
operation database already includes externally specified analytical floors,
interpolation and empirical terms. This study adds no fitted SimLLM timing
term. It does not establish new physical calibration, qualify a larger model,
or rescore the historical mixed frontier or void study.

## Immutable authority and supported paths

Use the existing calibration `RecordObject` canonical bytes and external
SHA-256 identity. The record carries all eight original source values, units,
phase roles, source file hashes and attribution. Values used in arithmetic
have exact binary64 hexadecimal spellings. Interventions keep the original
source values, declare their changed values and reference a parent record.
Changing a value or any provenance member changes the identity.

The optional record binds through `ExternalQwen32BDeploymentBinding` and the
existing external pass model. Admission checks the complete imported source
closure and the current public model and system state. Recheck that state
before a cached model can serve another value. An explicit parameter is legal
only if it exactly matches the selected record value; changing a parameter
requires a derived record. Missing, malformed, conflicting or mismatched
records reject before pricing. No implicit record is selected.

Every record-enabled memory operation, including attention normalization,
rotary-position work and cache writes, uses the resolved memory factors.
The absent-record route preserves the original arithmetic and parameter
semantics, including aggregate counterfactuals. Record-enabled aggregate
pricing shares only memory bandwidth, memory constant and context-attention
extra correction. Its existing mixed-step and queue rules remain explicit;
the other five disaggregated adjustments are inactive there.

Record-enabled services join the composition digest to their existing keys
and source descriptions. That identity reaches `BatchServicePoint`,
`TermEstimate`, estimator stamps and the new read-only capacity and first-token
projections. Reject values from a different shape, source or record even when
their durations happen to match. Ordinary record-absent serialized field
presence, source strings, keys and values remain unchanged.

The serving projections consume completed existing estimator values. They
introduce no scheduler, queue, timing owner or invented arrival load. The
external autoscaled first-token heuristic remains separate from isolated
prefill service and from a simulated request's causal first-token latency.

## Prospective mechanisms and bounds

For all 13 service shapes, cross the memory bandwidth scales 0.4 and 0.8 with
the per-operation constants zero and 3 microseconds. No operation shape or
measured database row changes. With all other factors fixed, each service is
of the form `K + A / scale + B * constant`, with nonnegative coefficients.
Halving the scale strictly increases service; adding the constant strictly
increases it. The two memory increments are independent of each other.

The constant coefficient before the phase correction is 193 for decode:
one embedding and three memory visits per each of 64 layers. Prefill adds
12 attention-auxiliary visits per layer, multiplied by the 1.1 attention
extra correction. The coefficients after phase correction are therefore
`193 * 1.08` and `(193 + 12 * 64 * 1.1) * 1.1`. Compare the observed constant
increments against those independent counts with the frozen floating-point
rounding allowance. Memory scaling increments follow the byte equations in
the JSON freeze. These are behavioral relations, not new fitted parameters.

Floor: each rank must at least stream its share of the 64 layers' three
8-bit feed-forward matrices at the declared 4.8 TB/s peak memory rate.
Floor: their multiply-add work alone costs at least two operations per weight
and active token at the declared 1.978 petaflop/s 8-bit peak. Use the greater
of these two floors, with effective prompt tokens in prefill and batch size
in decode. They deliberately omit attention, embeddings and scale metadata,
so they are conservative lower bounds, not complete work estimates.

Ceiling for this bounded intervention: no term exceeds twice its accepted
baseline service because only the inverse bandwidth factor can double, the
nonnegative operation constant never exceeds baseline and all other positive
terms stay fixed. This is a bound on the specified composition, not a
universal upper bound on real GPU latency. Report all values against both
floors and this ceiling before scoring their numerical relations.

For the TP4, batch-26 decode point, cross prefill engine counts 1 and 2,
decode engine counts 1 and 2, prefill rate factors 0.45 and 0.9, and decode
rate factors 0.46 and 0.92. Compute exact capacities using integer-picosecond
service and `Fraction.from_float` factors. Increasing either engine count or
its rate factor doubles that pool's capacity exactly. The served capacity
is their minimum, so it increases until the other pool limits it and then
stops. Both limiter states must occur. Preserve the source estimator stamps
and joined composition identity on every row.

For each of the three prefill tensor widths, compare autoscale 1.0 and 1.8.
The binary64 product is exact under the original operator and converts to
picoseconds only at the existing boundary. It changes the external first-token
heuristic and leaves isolated prefill and decode service unchanged. These
checks make all three serving-only factors positively reachable, which the
historical decode sensitivity alone cannot demonstrate.
